# i18n: typed TS catalog and ICU via `intl-messageformat`

## Decision

The rule applies to everything user-visible in `app/` and to every server
error body that a human reads. UI languages are German (primary language) and
English.

User-visible texts live in the catalog `app/src/i18n/` — `de.ts` and
`en.ts`, both as TS objects. `de.ts` defines the key set
(`MessageKey = keyof typeof de`); every further language is a total
`Record<MessageKey, string>`. A missing key and a key that exists only in
`en.ts` are both a **type error** — no build step, no extraction tool, no
runtime fallback to another language.

Interpolation and plurals are **ICU MessageFormat** via
**`intl-messageformat`**: `{count, plural, one {# Eintrag} other {# Einträge}}`
— the form is in the sentence, where translators see it.

### Rules in code

- In components, `t(key, params)` comes from `useT()`/`useI18n()`. Pure
  helpers in `app/src/lib/` receive the translator as an argument — the lib
  level never decides which language the UI runs in.
- A value with markup in the middle of a sentence is formatted into parts via
  `tNode`, never glued together from two half-sentences.
- Times and dates go through `Intl` with the selected language, not through
  hand-built formats.
- Enum labels shared by many views (scene and NPC status in
  `app/src/scene/scene-status.ts` and `app/src/npc/npc-status.ts`) come from
  the catalog; the helpers take `t: Translate` as an argument for that. An
  unknown value is shown verbatim — the row is the truth.

### The language is an instance setting on the server

- `GET/PUT /api/settings`, stored as the row `setting:locale` in `meta`. No
  localStorage. Without a stored value the app follows `navigator.language`
  (`de*` → de, otherwise en) and writes nothing.
- **The first paint is gated.** While `GET /api/settings` is running,
  `I18nProvider` renders nothing language-dependent, but a neutral shell (only
  the wordmark glyph). Below the provider `isPending` is always `false`; no
  view handles a "language not yet known" state.
- **`<html lang>` follows the language,** set in the provider.
- **The language choice is on the settings page** `/settings`,
  campaign-independent, reachable via a gear icon on the right of the top bar
  (icon-only at every width). The page holds only settings of the
  installation; campaign content such as glossary and campaign knowledge has
  its own pages (`decisions/resources`).
- **Where there is no chrome, the switch additionally appears inline** —
  `app/src/components/LanguageSwitch.tsx` (native radios) as a footer on the
  cold start (no campaign, no switcher) and on the mobile start screen, which
  takes the place of the top bar and its gear below `md`. All surfaces read
  and write the same server setting via `useI18n`.

### The server is language-free

Every error body that a human reads carries a stable `code`
(`shared/src/error-codes.ts`) plus the parameters its sentence needs; the
`error` text stands beside it as an **English technical fallback** (curl,
log, third-party client). The app builds the sentence from the catalog
(`app/src/i18n/server-errors.ts`, keys `server.<code>`). It **degrades**: no
code, an unknown code or a body without the promised parameters fall back to
the English `error` text, then to the view's generic sentence — never to an
empty message. Codes are **append-only**: an old code keeps its meaning and
parameters. Texts that appear only in the CLI or log (`grimoire seed`, boot)
are English and have no code.

### Lint gate

`react/jsx-no-literals` (`bun run lint`, in CI) is set to `error` everywhere
in `app/src` (`eslint.config.js`). The `allowedStrings` list is the only
exception and carries exclusively non-copy: separators, key names
(`⌘K`, `esc`) and Markdown markers shown in the block composer (`[!`, `]`).
ESLint stays on `^9`: `eslint-plugin-react@7.37.5` does not know ESLint 10 as
a peer, and the gate consists of a rule of this plugin. It is raised as soon
as the plugin lists ESLint 10 as a peer.

## Why

**Not `i18next`:** It brings its own resource, namespace and backend model
(plus `react-i18next` for the hook) for problems that a single-user tool with
two languages and one bundle does not have; plurals work via key suffixes
(`_one`/`_other`) instead of in the text; and type safety requires module
augmentation and generated types instead of a `keyof`.
`intl-messageformat` is a pure formatter (one package, ≈10 kB gzip, no
peers); catalog and loading stay in our hands.

**No locale downloads:** Plural categories come from the built-in
`Intl.PluralRules`, date and number formats from `Intl` — nothing is loaded
at runtime, which a self-hosted, offline-capable tool must not do anyway.

**Gated first paint:** Otherwise an instance set to German in an English
browser would show English chrome for one frame and then swap it.
**`<html lang>`:** a wrong `lang` makes the screen reader pronounce the page
wrongly and hyphenate it wrongly; `index.html` can carry only a static value.

**Settings page instead of switcher menu:** The switcher menu is where one
picks a campaign; an instance-wide setting in it is hard to find and
categorically wrong. On mobile the switch appears inline instead of as a
link, because the mobile surface is for looking things up and jotting things
down (docs/UI-BRIEF.md), and the reading language is the one setting a phone
plausibly needs.

## Consequences

- Every new error code needs a catalog entry in both languages; if it is
  missing, the app degrades to the English `error` sentence.
